# 제조데이터 분석 프로세스

일반적인 데이터분석 프로세스(문제정의→EDA→모델링→평가)를 그대로 쓰지 않고, KAMP 50개 데이터셋에서 반복적으로 확인된 제조데이터 특성을 반영해 설계한 프로세스입니다. **특정 머신러닝 알고리즘을 지정하지 않습니다** — "무엇을 예측/분류/최적화할지"를 결정하는 것까지가 이 프로세스의 범위이고, 세부 모델 선택은 그 다음 문제입니다.

---

## 1. 왜 일반 프로세스를 그대로 안 쓰는가 — 제조데이터의 반복 특성

| # | 특성 | 확인된 근거 | 프로세스에 반영할 점 |
|---|---|---|---|
| 1 | 공정·설비를 먼저 이해해야 함 | 같은 컬럼명(`Temp` 등)도 공정마다 의미가 다름. 데이터셋 이름과 실제 분석 유형이 어긋나는 경우도 있음(예: "자원최적화"라는 이름인데 실제로는 설비 이상탐지) | 데이터를 열기 전에 공정·설비부터 확인 |
| 2 | 한 행의 단위(grain) 확인 필요 | 시점 단위 / Lot 단위 / Shot 단위 / 파형 단위가 데이터셋마다 다름. 같은 데이터셋 안에서도 파일마다 단위가 다른 경우 있음(조건표 vs 시계열) | 단위를 먼저 확정하고, 다르면 결합 키를 정함 |
| 3 | 공정/품질/설비 데이터의 성격이 다름 | 같은 라인에서도 어떤 파일은 품질 라벨이 있고 어떤 파일은 설비 진동값만 있음 | 데이터 성격 분류가 EDA보다 먼저 |
| 4 | 시간축 유무·종류가 다름 | 연속 모니터링형 vs 파형형 vs 순서 무관형(Shot 단위) | train/test 분리 방식을 시간축 종류에 맞게 결정 |
| 5 | 라벨 유무가 다름 | 라벨이 이미 있음 / 다른 파일과 결합 필요 / 아예 없음(비지도 이상치탐지로 접근) 세 갈래가 실제로 존재 | target 확정 방식을 미리 분기 |
| 6 | 결측치·이상치는 원인이 있는 경우가 많음 | 여러 센서 병합 시 수집주기 차이로 생기는 결측, 설비 정지 구간 등 | 원인을 먼저 설명하고 처리 방법을 정함 |
| 7 | 불균형 데이터가 흔함 | "정상이 90% 이상" 같은 공식 설명이 다수. 그래서 비지도 이상치탐지 접근이 많이 쓰임 | 평가 지표·접근법을 불균형 정도에 맞게 분기 |
| 8 | 공정변수-품질 관계는 "관리 가능한 구간"까지 연결해야 함 | 다수 데이터셋이 "변수 중요도 확인 → 정상 구간 역산" 방식을 취함 | 상관관계 계산에서 끝내지 않고 관리 구간 제시까지 |
| 9 | 설비 이상과 품질 이상은 원인이 다를 수 있음 | 같은 설비의 "가생산(예열)"과 "진짜 불량"은 겉보기엔 비슷해도 다른 문제 | 이상 신호가 설비 문제인지 제품 문제인지 항상 구분 |
| 10 | 결과는 현장 실행으로 연결되어야 함 | 공식 결과 서술이 "비용절감", "생산차질 방지" 같은 실행 관점으로 끝남 | 마지막 단계를 수치가 아니라 실행 문장 + 한계로 마무리 |

## 2. 최종 프로세스

```
[0] 도메인·설비 이해
      데이터를 받으면 행·컬럼을 먼저 훑으며 "어느 공정, 어느 설비 데이터인가" 판단
      ↓
[1] 문제정의
      "이 분석으로 현장의 어떤 의사결정을 바꾸고 싶은가"를 한 문장으로
      ↓
[2] 데이터 성격 점검 ── 여기서 경로가 갈림 ──┐
      · 라벨이 컬럼으로 이미 있는가?            │
      · 라벨이 다른 파일에 있어 결합이           │
        필요한가? (날짜/Lot/ID 공통키 확인)      │
      · 라벨이 아예 없는가?                      │
      · 불균형 정도는?                           │
      ↓                                          ↓
[3A] (라벨 있음/결합 가능)                  [3B] (라벨 없음)
     라벨-변수 결합 및 정합성 확인                "정상"의 기준부터 정의
      ↓                                          ↓
[4] 데이터 품질 점검 (공통)
      결측·이상치·중복 → 제거/대체 전에 "왜 생겼는가"부터 확인
      ↓
[5] EDA (기술통계, KAMP AI-PaaS/Note 활용 가능)
      기초 분포·상관관계 확인 + 불균형 재확인
      ↓
[6] Feature Engineering
      원본을 분석 단위(Lot/Shot)에 맞는 요약변수·파생변수로 변환
      ※ 이 시점부터 "이 변수, 다른 공정에도 있을 법한가"를 함께 기록 (확장성 대비)
      ↓
[7] 분석 / 모델링
      [3A] 지도학습형 분석 (분류·회귀 등) / [3B] 비지도 이상탐지형 분석
      ↓
[8] 평가
      불균형이 있었다면 정확도 단독이 아니라 그에 맞는 지표로 판단
      ↓
[9] 설비 이상 vs 품질 이상 재확인
      지금 잡은 이상/불량이 설비 문제인지, 제품 문제인지,
      혹은 의도된 정상 상태(예열 등)인지 도메인 지식으로 재검토
      ↓
[10] 제조적 해석 + 현장 적용
      통계 용어가 아니라 공정 용어로 재설명, "현장의 누가 무엇을 다르게 해야 하는가"
      ↓
[11] 확장성 정리
      6~10단계에서 메모해둔 "다른 공정·업종에도 통할까"를 취합해 정리
```

## 3. 단계별 상세 (무엇을 / 왜 / 특별히 확인할 것 / 건너뛰면 생기는 문제)

| 단계 | 무엇을 하는가 | 왜 필요한가 | 제조데이터에서 특별히 확인할 것 | 건너뛰면 생기는 문제 |
|---|---|---|---|---|
| 0. 도메인·설비 이해 | 업종·공정·설비 파악, 정상 흐름을 한 문장으로 정리 | 컬럼명이 공정마다 의미가 달라서, 모르면 해석 자체가 불가능 | 컬럼명 속 전문용어(Zone, Spindle, pH, Shot 등)를 용어사전에서 확인 | 물리적으로 말이 안 되는 상관관계를 인과관계로 착각 |
| 1. 문제정의 | 분석으로 바꾸고 싶은 현장 의사결정을 한 문장으로 | 같은 데이터도 질문에 따라 완전히 다른 분석이 됨 | 품질예측/설비상태파악/조건추천 중 어디에 가까운지 구분 | EDA 중 계속 곁길로 새어 결론 없는 분석이 됨 |
| 2. 데이터 구조·성격 파악 | 행 단위, 시간축 종류, 공정/품질/설비 성격, 라벨 유무 확정 | 이후 모든 집계·분리 방식을 결정 | 여러 파일의 단위가 다르면 조인 기준(Lot/날짜/ID)을 미리 적어둠 | 단위 착각으로 집계가 통계적으로 무의미해짐 |
| 3A/3B. 라벨 결합 또는 정상 정의 | 라벨-변수 정합성 확인 또는 정상 패턴/이상판정 기준 설계 | 라벨 없는 데이터는 "정상 정의"가 분석의 절반 | 설비 예열구간처럼 "비정상처럼 보이지만 정상"인 특수 구간 확인 | 라벨이 밀려 결합되거나, 정상 정의가 애매해 이상탐지 결과가 흔들림 |
| 4. 데이터 품질 점검 | 결측·이상치·중복의 원인 추적 | 제조 결측/이상치는 원인이 있는 신호인 경우가 많음(설비정지 등) | 원인이 분석 목적과 관련된 신호인지, 단순 노이즈인지 구분 | 중요한 신호(설비 정지 등)를 실수로 지워버림 |
| 5. Feature Engineering | 시계열 → Lot/Shot 단위 요약·파생변수 변환 | 원본 시계열은 그대로 Lot 단위 분석에 못 씀 | 목표-실제 편차, Zone 간 편차 등 공정 지식 반영 변수 우선 | 단위 불일치로 분석 불가 또는 해석 불가능한 통계값만 남음 |
| 6. 분석/모델링 | 문제정의·데이터성격에 맞는 분석 수행 | 앞 단계가 "올바른 질문에 올바른 데이터로" 분석하기 위한 준비였음 | 시간축이 있으면 시간 순서를 지켜 train/test 분리 | 앞 단계 오류가 결과에 그대로 반영되어 그럴듯하지만 틀린 결론 |
| 7. 평가 | 결과가 질문에 답이 되는지, 통계적으로 믿을만한지 확인 | 불균형 데이터는 흔한 지표가 오해를 부를 수 있음 | 소수 클래스(불량/이상)를 얼마나 잘 잡는지 중심으로 확인 | 항상 "정상"이라 답해도 정확도가 높은, 쓸모없는 결과를 그대로 전달 |
| 8. 제조적 해석 | 결과를 공정 용어로 재설명, 설비/품질 이상 재구분 | 같은 신호가 다른 원인(예열 vs 불량)을 가리킬 수 있음 | 중요 변수가 원인 변수인지 결과성 변수인지 공정 흐름과 대조 | 관리해도 소용없는 변수를 관리 대상으로 잘못 추천 |
| 9. 현장 적용 + 한계 정리 | "누가, 무엇을, 언제 다르게 해야 하는가" + 놓친 부분 기록 | 실행 가능한 형태가 아니면 현장에 반영되지 않음 | 실행할 사람(작업자/설비관리자/공정엔지니어)을 명시 | 아무도 실행하지 않는 "보고서용 분석"이 됨 |

## 4. 대회 평가지표와 단계 매핑

시간이 부족할 때 어디에 힘을 더 줄지 판단하는 용도입니다.

**서면평가 (정량 30 + 정성 70)**

| 지표 | 배점 | 기여 단계 |
|---|---|---|
| AI 성능 정확도 | 30 | 6.분석/모델링, 7.평가 |
| 제조현장 문제 이해도 | 10 | 0.도메인 이해 |
| 제조AI데이터셋 이해도 | 10 | 0, 2, 4 |
| 문제 정의 체계성 | 10 | 1.문제정의 |
| 분석모델 독창성 | 10 | 5.파생변수, 6.모델링 |
| 분석 과정 타당성 | 10 | 2~7 전 과정의 논리적 일관성 |
| 결과해석 우수성 | 10 | 8.설비/품질 이상 구분, 제조적 해석 |
| 결과물 작성 충실성 | 10 | 보고서 전체 |

**발표평가 (정성 100)**

| 지표 | 배점 | 기여 단계 |
|---|---|---|
| 발표능력 우수성 | 10 | 발표 자체 |
| 문제 해결 독창성 | 20 | 1.문제정의, 5.파생변수 |
| 분석 과정 적절성 | 20 | 2~7 |
| 분석모델 적용 가능성 | 20 | 9.현장 적용 |
| **분석모델 확장성(사업성 포함)** | **30** | **11.확장성 정리 — 단, 6단계부터 누적 준비 필요** |

> 발표평가에서는 **확장성이 30점으로 단일 최고 배점**입니다. 시간이 부족하면 모델 성능을 더 짜내기보다, "이 결과가 왜 다른 공정·업종에도 통하는가"를 설득력 있게 정리하는 쪽이 점수에 유리합니다. 확장성은 마지막에 몰아서 생각하지 말고 파생변수 설계 단계부터 계속 메모해두세요.

## 5. 실전 체크리스트

- [ ] 이 데이터는 어느 공정군에 가장 가까운가?
- [ ] 이 분석으로 현장의 어떤 의사결정을 바꾸고 싶은가? (한 문장)
- [ ] 라벨은 있는가 / 다른 파일과 결합해야 하는가 / 없는가? 불균형 정도는?
- [ ] 결측·이상치가 있다면 원인이 뭐라고 설명할 수 있는가?
- [ ] 지금 만드는 파생변수가 다른 공정에도 있을 법한 변수인가? (메모)
- [ ] 불균형을 고려했을 때 이 평가지표가 적절한가?
- [ ] 지금 잡은 이상/불량이 설비 문제인가, 제품 문제인가, 의도된 정상 상태인가?
- [ ] 현장의 누가, 무엇을, 언제 다르게 해야 하는가?
- [ ] 확장성 아이디어를 발표자료에 별도로 정리했는가?
