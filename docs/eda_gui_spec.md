# KAMP 제조 CSV 기초 분석 GUI 도구 — 설계 명세 (v2)

> KAMP 2026 제6회 K-AI 제조데이터 분석 경진대회 준비 과제(① 50개 데이터셋으로 제조 도메인 이해, ② 우리만의 데이터분석 프로세스 정의)의 실행 도구로 개발한다.
> 관련 문서: [`../notion/3_데이터분석_프로세스.md`](../notion/3_데이터분석_프로세스.md) · [`../reports/04_my_manufacturing_data_analysis_process.md`](../reports/04_my_manufacturing_data_analysis_process.md) · [`../reports/01_kamp_50_domain_map.md`](../reports/01_kamp_50_domain_map.md) · [`../reports/02_manufacturing_domain_overview.md`](../reports/02_manufacturing_domain_overview.md) · [`../reports/03_learning_order.md`](../reports/03_learning_order.md)
> **v2 변경 배경**: v1은 label/ID/Lot·Shot/Set-Actual을 "신뢰도가 낮은 자동 후보"로라도 프로그램이 제시하는 구조였다. 이번 버전은 그 자동 추론 자체를 전부 제거하고, `dataset/` 폴더의 실제 CSV 7개를 직접 열어 확인한 결과를 근거로 MVP 범위를 재확정했다. 코드는 포함하지 않는다.

## 1. 프로젝트 목적

> KAMP 제조 CSV를 업로드하고, 사용자가 원하는 분석 목적과 변수를 선택하면 기초 기술통계와 적절한 시각화를 제공하는 GUI 도구.

**목표로 하지 않는 것**
- 데이터 의미 자동 추론(공정/품질/설비 성격, 제조 문제 유형)
- 분석 목적 자동 추론
- target/label, ID, Lot/Shot, Set/Actual **자동 판별**
- 자동 머신러닝, 예측, 예지보전 모델
- 모델 기반 이상탐지(Isolation Forest, LOF, Autoencoder 등)
- 범용 BI 플랫폼, 종합 Auto EDA 플랫폼

프로그램의 역할은 **데이터의 의미를 알아내는 것이 아니라, 실제 CSV 구조를 있는 그대로 보여주고, 사용자가 선택한 목적·변수에 맞는 기초 통계·시각화를 수행하는 것**이다. 문제정의, 라벨/시간축 해석, 설비 이상 vs 품질 이상 판단(`3_데이터분석_프로세스.md`의 [1],[3A/3B],[9]단계)은 전부 사람의 몫으로 남긴다.

## 2. KAMP 메타정보 활용

KAMP 공식 상세 페이지는 각 데이터셋의 목적·공정·수집방법·변수 설명·데이터 형태를 이미 제공하며, 팀 자체 자료(`01_kamp_50_domain_map.md`, `02_manufacturing_domain_overview.md`)도 이를 정리해두었다. 이 도구는 그 정보를 **대체하지 않는다**:

- 도구가 하는 일: 업로드된 CSV **파일 자체의 구조**(행/열, dtype, 결측, 분포)를 사람이 코드 없이 확인하게 함
- 도구가 하지 않는 일: "이 컬럼은 온도 센서다", "이 데이터는 품질 데이터다" 같은 **의미 해석** — 이건 KAMP 공식 문서와 팀 자료를 사람이 참고해서 판단
- 따라서 GUI 어디에도 "공정/품질/설비 성격 선택" 같은 도메인 분류 UI를 두지 않는다. 그 판단은 도구 밖(공식 문서, 팀 자료)에서 이미 이뤄진 상태로 CSV를 가져온다고 가정한다.

## 3. CSV 프로파일링

업로드 직후 자동으로 수행하는 **구조 파악**이다. 아래 항목은 전부 dtype·통계 수준의 사실이며, 의미 판단이 아니다.

| 항목 | 방법 |
|---|---|
| 행 수 / 열 수 | `df.shape` |
| 컬럼명 / dtype | 원본 그대로 노출(수치형/범주형/datetime/텍스트로 자동 분류하되, 사용자가 재분류 가능) |
| 결측치 | 컬럼별 개수·비율 |
| 중복행 | 전체 컬럼 기준 개수 |
| unique 개수 | 컬럼별 |
| 기본 기술통계 | 수치형 `describe()`, 범주형 `value_counts()` 요약 |

**실제 KAMP CSV를 열어보며 확인된, 프로파일링 단계에서 반드시 처리해야 하는 3가지 현실 문제** (15장 검증 결과에서 상세):

1. **인코딩 문제**: `05_Welding`의 `scaled_data.csv`를 열어보면 한글 헤더가 깨져(`"\xb9\xac\xb1\xd7..."`류 mojibake) 표시된다. UTF-8 우선 시도 → 실패 시 CP949 재시도 → 둘 다 실패하면 사용자가 인코딩을 수동 선택하는 폴백이 실제로 필요하다.
2. **비표준 헤더 구조**: `37_주조_품질보증`의 `DieCasting_Quality_Raw_Data.csv`는 **1행이 카테고리 태그(`Process,Process,...,Sensor,...,Defects,...`), 2행이 실제 컬럼명**인 2행 헤더 구조다. `pd.read_csv()`를 기본값으로 그대로 실행하면 1행이 컬럼명으로 잘못 들어간다. → 업로드 직후 원본 첫 3~5행을 미리보기로 보여주고, "헤더로 사용할 행 번호"를 사용자가 지정할 수 있어야 한다(기본값 1행).
3. **헤더 없는 CSV**: `03_CNC`의 `Y_train.csv`는 헤더 없이 숫자 데이터만 있다(`1.0,0.0` 형태로 시작). 기본 파싱 시 첫 데이터 행이 컬럼명으로 오인된다. → 첫 행이 전부 숫자로만 구성되면 "이 파일은 헤더가 없는 것으로 보입니다. 헤더 없이 불러올까요?"라는 확인을 제공한다.

이 세 가지는 자동으로 "정답"을 추론하지 않는다 — **미리보기 + 사용자 확인** 방식으로만 대응한다(2장 원칙과 일관).

## 4. 사용자 입력

프로그램이 자동 제공하는 것(3장)과 명확히 분리해, 아래는 **전부 사용자가 직접 지정**한다. 자동 후보 제시(v1의 "추정 배지")도 두지 않는다 — 드롭다운에는 dtype으로 걸러진 목록만 보여준다(예: 시간축 드롭다운은 datetime 파싱 가능한 컬럼만 나열 — 이건 구조적 필터링이지 "이게 시간축이다"라는 의미 판단이 아니다).

| 사용자가 선택 | 방식 |
|---|---|
| 분석 목적 | 5장의 목적 카드 중 선택 |
| 분석할 변수 | 수치형/범주형 컬럼 목록에서 직접 선택(다중 선택 가능) |
| 시간축 | datetime 파싱 가능 컬럼 목록에서 선택 (자동 추천 없음) |
| 그룹/라벨 컬럼 | 전체 컬럼 목록에서 선택 (자동 추천 없음) |

## 5. 분석 목적

원안의 6개(데이터 기본 파악 포함)에서 **"데이터 기본 파악"을 목적 선택 메뉴에서 분리**했다 — 이건 3장 프로파일링으로 업로드 직후 항상 보여주는 공통 정보이지, 사용자가 매번 "선택"해야 하는 목적이 아니기 때문이다. 남은 4개 목적 + 실데이터 검증을 거친 "그룹별 비교" 1개, 총 5개가 최종 목적 메뉴다.

| 목적 | 정의 | 활성화 조건 | 비활성 시 안내 |
|---|---|---|---|
| 변수 분포 확인 | 개별 변수의 분포(치우침, 범주 비율) 확인 | 수치형 또는 범주형 컬럼 1개 이상 | - |
| 변수 간 관계 확인 | 두 개 이상 변수의 상관 패턴 확인 | 수치형 컬럼 2개 이상 | "수치형 변수가 1개 이하라 상관관계를 볼 수 없습니다" |
| **그룹별 비교** | 사용자가 지정한 그룹 컬럼 기준으로 수치형 변수의 분포를 비교 (15장 검증 결과 MVP 포함 확정) | 사용자가 그룹으로 쓸 컬럼을 직접 선택 | "그룹으로 쓸 컬럼이 지정되지 않았습니다 — 비교할 컬럼을 선택하세요" |
| 시간에 따른 변화 확인 | 시간 흐름에 따른 추세 관찰(설비 이상 여부를 판단하는 기능이 아니라 **추세를 보여주는** 기능) | 시간축 컬럼을 사용자가 지정 | "시간축으로 쓸 컬럼이 지정되지 않았습니다" |
| 통계적 이상치 탐색 | IQR 기준 극단값 탐색(모델 기반 이상탐지 아님) | 수치형 컬럼 1개 이상 | - |

## 6. 분석 모듈

### 모듈 A — 변수 분포
- 수치형: `count, mean, std, min, 25%, median, 75%, max, skew, missing` + 히스토그램 + 박스플롯
- 범주형: `value_counts, percentage` + 막대그래프
- 제외(MVP): 파이차트(카테고리 많으면 막대그래프보다 가독성 낮음)

### 모듈 B — 변수 간 관계
- Pearson 상관계수 + correlation heatmap
- 사용자가 선택한 두 변수의 scatter plot
- 제외(MVP): 전체 pairplot(컬럼 수십 개인 제조 데이터에서 렌더링 부담·가독성 문제 — `42_기계부품품질보증`처럼 50개 이상 컬럼을 가진 데이터로 실측 확인), 자동 유의성 검정

### 모듈 C — 그룹별 비교 *(실데이터 검증 후 MVP 포함 확정 — 15장 참고)*
- 사용자가 **그룹 컬럼 1개 + 분석할 수치형 변수**를 직접 선택 (프로그램은 이 컬럼이 "라벨"인지 "품질"인지 판단하지 않는다)
- 그룹별 count, 그룹별 비율(%), 그룹별 mean/std, 그룹별 boxplot, 필요 시 그룹별 histogram
- 제외(MVP): t-test 등 가설검정 자동화 — 사용자 지시대로 하지 않음

### 모듈 D — 시간에 따른 변화
- 사용자가 지정한 시간축 + 수치형 변수로 시간순 정렬 후 line chart
- 선택적으로 rolling mean, 시간축 기준 결측 구간 표시
- "설비 이상 판단" 기능이 아니라 **관찰 기능**임을 UI에 명시

### 모듈 E — 통계적 이상치 탐색
- IQR(1.5×IQR) 기준 이상치 개수/비율 + boxplot
- 시간축이 지정된 경우 이상치 위치를 시계열 위에 표시
- 제외: Isolation Forest, LOF, Autoencoder, 자동 이상구간 탐지
- **UI 고지 문구(필수)**: "IQR 기준의 통계적 이상치이며, 제조공정의 실제 이상이나 설비 고장을 의미하지 않습니다."

### MVP에서 완전히 제외 (v1의 모듈 7·8)
- Set vs Actual 편차, Lot/Shot 단위 비교, 그리고 그 자동 추론 전부
- 근거: 15장 검증에서 확인했듯 이 둘을 의미 있게 쓰려면 대부분 다중 파일 조인(`03_CNC`처럼 조건표와 시계열이 분리된 경우)이 선행돼야 하는데, 다중 파일 조인 자체가 이번 MVP 범위(단일 CSV 업로드) 밖이다. 향후 실제 사용 중 필요성이 재확인되면 그때 검토한다.

## 7. GUI 흐름

```
CSV 업로드
   ↓
기본 데이터 정보 (3장 프로파일링 — 자동, 목적 선택과 무관하게 항상 표시)
   ↓
분석 목적 선택 (5장, 5개 카드 — 조건 미충족 시 비활성화 + 사유 표시)
   ↓
필요한 변수 선택 (그룹 컬럼 / 시간축 / 분석 변수 — 목적에 따라 다름, 4장)
   ↓
분석 실행
   ↓
기술통계 + 시각화 결과
```

- 목적을 변경해도 업로드한 데이터와 프로파일링 결과는 재계산하지 않고 유지한다(Streamlit `st.session_state`).
- 업로드 화면에서 3장의 인코딩/헤더 확인 단계를 거친 뒤에만 프로파일링으로 넘어간다.

## 8. 대용량 데이터 처리

**실측 근거** (`dataset/` 폴더 직접 확인):

| 데이터셋 | 파일 | 크기 | 행 수 |
|---|---|---|---|
| `08_Meltingtank` | `melting_tank.csv` | 35.2MB | 835,201행 × 7열 |
| `11_Drier` | `drying_actuator1/2.csv` | 71.7MB / 72MB | (열 적고 행 매우 많음) |
| `41_전자부품_배터리팩_품질보증` | 폴더 전체 | 631MB / 125파일 | 셀 176개 × 전압 등 열이 많음 |

이 규모(개별 파일 최대 수십~100MB대)에서는 **청크 읽기·분산처리 같은 무거운 인프라가 불필요**하다는 것을 확인했다. pandas로 전체 로드가 가능하고, `melting_tank.csv`(83만 행)처럼 행이 매우 많아도 열이 7개뿐이면 `describe()` 등 집계 연산은 수 초 내 끝난다.

**적용 원칙**:
1. 기술통계는 **전체 데이터 기준**으로 계산한다.
2. 시각화(산점도, 시계열 라인)만 다운샘플링한다 — 병목은 로드가 아니라 렌더링이다. 수십만 포인트를 브라우저에 그대로 그리면 느리고 의미도 없다.
3. 행 수 임계치(예: 10만 행) 초과 시 "차트는 샘플 기준으로 표시됩니다" 배지를 표시해, 통계와 시각화의 기준이 다르다는 것을 사용자가 착각하지 않게 한다.
4. 청크 읽기·스트리밍 집계 같은 복잡한 처리는 실제로 더 큰 파일(예: 수 GB급)이 확인되기 전까지는 제안하지 않는다.

## 9. MVP 범위

### 공통 (항상 실행)
- CSV 업로드 (인코딩 자동감지 + 수동 폴백, 헤더 행 지정, 헤더 없음 옵션 — 3장)
- 데이터 기본 정보, 기술통계, 결측치, 중복, dtype

### 분석 (사용자가 목적 선택)
- 변수 분포 (모듈 A)
- 변수 간 관계 (모듈 B)
- 그룹별 비교 (모듈 C) — **실데이터 검증 후 포함 확정**
- 시간에 따른 변화 (모듈 D)
- 통계적 이상치 탐색 (모듈 E)

### 제외 (다음 버전 이후)
- Set/Actual, Lot/Shot 관련 기능 전부(자동/수동 불문)
- 다중 파일 업로드/조인
- 통계적 가설검정 자동화, 모델 기반 이상탐지
- 리포트 자동 생성(PDF/HTML 일괄 export)
- 사용자 정의 파생변수(임의 수식) 생성기

### 그룹별 비교 기능 최종 결론: **MVP 포함**

**결론**: 이름을 "품질/불량 비교"에서 "그룹별 비교"로 일반화하고, 완전히 사용자 지정 기반(자동판별 없음)으로 MVP에 포함한다.

**근거**:
1. `04_Molding`, `08_Meltingtank`처럼 단일 컬럼으로 깨끗한 그룹/라벨이 실제로 존재하는 데이터가 있고, 이 경우 "그룹별 분포 차이 + 그룹 비율"은 변수 분포·관계 모듈만으로는 볼 수 없는 정보다. 클래스 불균형 확인은 팀이 이미 정의한 프로세스 문서(`04_my_manufacturing_data_analysis_process.md` R7)에서도 핵심 요구사항으로 명시된 부분이다.
2. 구현 비용이 낮다 — 모듈 A(분포)의 통계·차트 로직에 `groupby`만 얹으면 된다.
3. 라벨이 없거나(`05,13`) 모호한(`37`, 후보 26개) 데이터에서도 "잘못 작동"하는 게 아니라 "고를 컬럼이 마땅치 않아 안 쓰는" 형태로 자연스럽게 축소되므로, 자동판별 없이 항상 켜둬도 안전하다.
4. 단, 프로그램은 어떤 컬럼도 "라벨"이라고 판단하지 않는다 — 사용자가 그룹 컬럼과 분석 변수를 직접 고르는 형태로만 제공한다(`37`처럼 후보가 26개여도 프로그램이 아니라 사용자가 고른다).
5. 가설검정(t-test 등)은 하지 않는다.
